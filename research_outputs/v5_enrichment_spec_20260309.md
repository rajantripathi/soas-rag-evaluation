# manual_eval_v5 Enrichment Specification

## Summary

This specification defines a deterministic enrichment script to be implemented as `scripts/build_manual_eval_v5.py` and executed on Isambard, where the full `manual_eval_v4` dataset and corpus files are available.

The script must preserve all v4 fields exactly and add three new fields to every item:

- `source_title`
- `difficulty`
- `quality_flag`

It must also emit a balanced internal QA sample, a validation report, and an internal schema note. Answer-bearing outputs remain untracked pending source and license clearance.

## Script Metadata

- Script path: `scripts/build_manual_eval_v5.py`
- Inputs:
  - `data/eval/manual_eval_v4.jsonl`
  - `data/processed/corpus_manual_v1_uzsupp_v2.jsonl`
- Outputs:
  - `data/eval/manual_eval_v5.jsonl`
  - `data/eval/sample/manual_eval_v5_sample.jsonl`
  - `results/reports/manual_eval_v5_validation.md`
  - `docs/dataset_card_v5.md`

## Output Schema

Each v5 item must preserve all original v4 fields:

- `id: str`
- `language: str`
- `domain: str`
- `question: str`
- `gold_answer: str`
- `cultural_specificity: str`
- `answerable: bool`
- `source_doc_ids: list[str]`

New required v5 fields:

- `source_title: str | null`
- `difficulty: Literal["easy", "medium", "hard"]`
- `quality_flag: str | null`

## Step 1: Source Title Resolution

### Function Signature

```python
def resolve_source_titles(
    eval_rows: list[dict],
    corpus_rows: list[dict],
) -> tuple[list[dict], dict]:
```

### Input Parameters

- `eval_rows`: rows loaded from `data/eval/manual_eval_v4.jsonl`
- `corpus_rows`: rows loaded from `data/processed/corpus_manual_v1_uzsupp_v2.jsonl`

### Behavior

- Build a corpus lookup keyed by `str(row["doc_id"])`
- For each eval item:
  - read `source_doc_ids[0]` if present
  - find the matching corpus row
  - extract `title` from the corpus row
  - normalize title extraction through existing project utility `src.datasets.detect_title`
- Write `source_title`:
  - resolved title string if found and non-empty
  - `null` if no match or empty title

### Output Format

- return enriched rows with `source_title`
- return resolution stats with:
  - total resolved
  - total unresolved
  - per-language breakdown

### Edge Cases

- `source_doc_ids` missing or empty: set `source_title = null`, count as unresolved
- corpus row found but title empty: set `source_title = null`
- multiple `source_doc_ids`: resolve only the first one; preserve the original list unchanged
- duplicate corpus `doc_id` values: fail fast with a validation error

### Validation Checks

- all items have a `source_title` field
- resolution counts sum to total rows
- report resolved vs unresolved counts overall and by language

## Step 2: Difficulty Classification

### Function Signature

```python
def assign_difficulty(row: dict) -> str:
```

### Input Parameters

- a single eval row after `source_title` enrichment

### Behavior

Apply a deterministic heuristic with no model calls:

- `easy` if:
  - question matches a simple definitional pattern
  - and `gold_answer` has 20 words or fewer
- `hard` if:
  - `domain == "history"`
  - or question contains any reasoning keyword:
    - English: `why`, `how important`
    - Uzbek: `tarixiy`, `tarixda`, `qanday bog'liq`
- `medium` otherwise

Recommended definitional patterns:

- English:
  - `What is `
  - `What are `
- Uzbek:
  - ` nima?`
  - ` qaysi til?`

### Output Format

- one of `easy`, `medium`, `hard`

### Edge Cases

- if a question matches both `easy` and `hard`, prefer `hard`
- trim whitespace before matching
- count words using whitespace tokenization after collapsing repeated whitespace

### Validation Checks

- every item has one valid difficulty label
- print difficulty distribution before writing output
- include per-language and per-domain distributions in the validation report

## Step 3: Quality Flags

### Function Signature

```python
def assign_quality_flags(rows: list[dict]) -> list[dict]:
```

### Input Parameters

- all v4 rows, before writing v5

### Behavior

Hardcode a seed-item flag map based on the audit:

```python
QUALITY_FLAGS = {
    "en_20": "domain_misclassification",
    "en_62": "domain_misclassification",
    "uz_82": "domain_misclassification",
    "uz_83": "domain_misclassification",
    "uz_78": "domain_misclassification",
    "uz_89": "domain_misclassification",
    "uz_71": "domain_misclassification",
    "en_61": "domain_misclassification",
    "uz_93": "question_quality",
}
```

Propagate flags to deterministic v4 variants generated by `build_manual_eval_v4.py`.

The propagation rule must mirror the existing builder:

1. group seed rows by `(language, domain)`
2. sort seed rows in each group by `id`
3. find the zero-based position of the flagged seed item
4. construct the variant ID as `{language}_{domain}_v4_{index:02d}`
5. assign the same `quality_flag` to that variant

Known propagated variant IDs from the current v4 build:

- `en_61` -> `en_governance_v4_19`
- `uz_71` -> `uz_institutions_v4_07`
- `uz_78` -> `uz_institutions_v4_08`
- `uz_82` -> `uz_institutions_v4_11`
- `uz_83` -> `uz_institutions_v4_12`
- `uz_89` -> `uz_institutions_v4_16`
- `uz_93` -> `uz_institutions_v4_18`

Items not present in the dictionary and not covered by propagation must receive `quality_flag = null`.

### Output Format

- all rows with `quality_flag` present

### Edge Cases

- if a seed item is flagged but its propagated variant is missing, fail validation
- if a row is assigned multiple conflicting flags, fail validation
- do not infer additional flags heuristically in this script; keep the assignment deterministic and auditable

### Validation Checks

- all rows have a `quality_flag` field
- count flagged vs unflagged rows
- report counts by flag value
- confirm propagated variant IDs exist and are flagged consistently

## Step 4: Validation

### Function Signature

```python
def validate_manual_eval_v5(rows: list[dict]) -> dict:
```

### Input Parameters

- fully enriched v5 rows

### Behavior

Confirm all of the following:

- exactly `400` rows
- all original v4 fields preserved without modification
- new fields `source_title`, `difficulty`, and `quality_flag` present on every row
- exactly `200` English and `200` Uzbek items
- exactly `50` items in each language-domain cell
- no duplicate IDs

### Output Format

- machine-readable validation stats dictionary
- human-readable markdown report at `results/reports/manual_eval_v5_validation.md`

### Edge Cases

- if any row count check fails, do not write output JSONL
- if any original field differs from v4, fail validation
- if `source_doc_ids` changes type or ordering, fail validation

### Validation Report Requirements

The markdown report must include:

- total row count
- duplicate-ID check
- language counts
- language-domain grid
- source-title resolution counts
- difficulty distribution
- quality-flag distribution
- list of unresolved `source_title` items, if any

## Step 5: Sample Dataset

### Function Signature

```python
def build_manual_eval_v5_sample(rows: list[dict]) -> list[dict]:
```

### Input Parameters

- validated v5 rows

### Behavior

Target output size: `30` items.

Selection rules:

- start from a target of 4 items per language-domain cell
- this yields 32 candidates across 8 cells
- drop the 2 least informative items after initial selection

Selection priority within each cell:

1. prefer `source_title is not null`
2. prefer a mix of `difficulty` values
3. ensure at least 2 total sample items have non-null `quality_flag`
4. avoid duplicate `quality_flag` items when possible unless needed for coverage

Recommended deterministic tie-breaker:

- sort candidates by:
  1. `quality_flag is null` ascending
  2. `source_title is null` ascending
  3. `difficulty` using order `hard`, `medium`, `easy`
  4. `id` ascending

After the 32-item draft is built:

- remove the 2 least informative items using the reverse of the selection priority
- do not remove the only flagged examples or the only example for a difficulty bucket within a cell if avoidable

### Output Format

- JSONL file at `data/eval/sample/manual_eval_v5_sample.jsonl`

### Edge Cases

- if a cell cannot provide 4 items with resolved titles, fill remaining slots with unresolved-title items
- if global flagged-item coverage is below 2 after initial selection, swap in flagged items deterministically
- if difficulty diversity cannot be satisfied within a cell, prefer title resolution first

### Validation Checks

- final sample size is exactly `30`
- sample spans all 8 language-domain cells
- sample contains at least 2 items with non-null `quality_flag`
- sample contains more than one difficulty level overall

## Step 6: Dataset Card

### Function Signature

```python
def write_dataset_card_v5(
    rows: list[dict],
    validation_stats: dict,
    sample_rows: list[dict],
) -> None:
```

### Input Parameters

- full validated v5 rows
- validation statistics
- selected v5 sample rows

### Required Sections

- Overview
- Languages
- Domains
- Schema
- Difficulty distribution
- Quality flags
- Changelog from v4 to v5
- Known limitations
- Publication boundary (no answer-bearing example entries while clearance is pending)

### Schema Section Requirements

List every field with:

- field name
- type
- brief description

This must include the new v5 fields:

- `source_title`
- `difficulty`
- `quality_flag`

### Quality Flags Section

Document:

- purpose of the field
- allowed values currently used:
  - `domain_misclassification`
  - `question_quality`
- counts per value

### Known Limitations Section

Carry forward the current limitations from `docs/limitations.md` and add the new audit findings:

- some benchmark items remain quality-flagged rather than removed
- retrieval and answer evaluation should still be interpreted separately when using stub generation
- English and Uzbek source schemas were historically asymmetric
- the internal QA sample is not a public release artifact

### Publication Boundary Section

Do not embed answer-bearing example entries in tracked documentation while source and license clearance is pending. Point readers to the retrieval-only files under `hf_dataset/` instead.

## Deliberate Exclusions From v5

The dataset card must explicitly document these excluded fields and their rationale.

### `evidence_text`

Exclude from v5.

Rationale:

- requires extracting the actual supporting span from corpus documents
- requires human verification for quality
- cannot be safely inferred from current benchmark metadata alone
- defer to v6

### `source_url`

Exclude from v5.

Rationale:

- requires verified URL resolution for each source
- cannot be generated reliably without document-level verification
- defer to v6

### `pair_id`

Exclude from v5.

Rationale:

- English and Uzbek halves are not parallel datasets
- English items come from TyDi QA and MIRACL and cover global subjects
- Uzbek items come from uz-wiki and focus heavily on Uzbekistan-specific material
- strict 1:1 pairing would mostly produce nulls and little analytical value
- defer to v6, where shared-topic items would need to be designed deliberately

## Acceptance Criteria

- `manual_eval_v5.jsonl` contains exactly 400 rows and preserves all v4 content
- every row has `source_title`, `difficulty`, and `quality_flag`
- the validation report shows language and domain balance
- the sample file contains exactly 30 rows with full-cell coverage
- the dataset card documents the new schema, limitations, exclusions, and examples clearly enough for external review
